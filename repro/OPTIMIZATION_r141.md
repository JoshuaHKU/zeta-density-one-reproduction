# `{6,2,2}` / `{4,4,2}` 加速：剖析、已实现的 2.5×，与后续杠杆

Round 141。数学：Claude；纲领指挥：Hongyi Yang。

## 1. 先剖析，再动手

在与 `{4,4,2}` 同构、低一维的 `{4,4}` 上对**单个 F-CYC 项**做 cProfile
（1.3 s，5768 次递归节点）：

| 部件 | 占比 |
|---|---|
| **精确单纯形的满维性判定**（`exact_lp.full_dimensional`，2792 次调用） | **44%** |
| `facets()` + `reduce_row()` 面枚举 | ~30% |
| 递归/记忆化簿记 | ~15% |
| **有理数算术本身**（gmpy2 mpq） | **< 10%** |

**结论直接改写了优化方向**：瓶颈是**判定调用的次数**，不是大整数运算。
换 C、上 CUDA 大整数库、多模数 + CRT——这些全部瞄准那不到 10%，
最好也就是 10% 的改善。而多模数还有个硬伤：单纯形要做**序比较**，
不是纯域运算，模 p 下没有序。

## 2. 已实现并验证的两条（合计实测 2.5×）

### (a) 满维性判定的**内容键记忆化**

`full_dimensional` 原来每次从零跑一遍精确单纯形。同一轨道内的几百个项
**共享全部基走位约束**，绝大多数面重复出现。改为按**内容规范化的键**
（每行归一到本原整数向量，取 frozenset）在**进程级**缓存判定结果——
不是按行序号，行序号只在单个 Polytope 内有意义。

实测命中率：**单项内 76%**，跨项升到 **86%** 并继续爬升。
单项 1.30 s → 0.83 s（冷）→ 0.52 s（热）。

### (b) 卦限的 σ ↔ −σ 折半

积分对全局反射 `v → -v` 不变：走位取负，spread 不变，故每个 overlap
因子不变，`|v|` 也不变；辅助变量按 `t → -t-1` 对应（仿射对合，Jacobian 1）。
该反射把卦限 σ 双射到 −σ，而带符号单项式 `sgn(σ)·Π x_c` 在两侧都等于
`Π |x_c|`。**故只需积分一半卦限再乘 2，是精确的 2×**，凡含 size-2 块的类都适用。

逐项核验：`{4,2}` 与 `{2,2,4}` 的每个 σ 与 −σ **逐条相等**。

### 回归

| 检验 | 结果 |
|---|---|
| 单项 A/B（`{2,2,4}`） | 0.54 s → 0.19 s，值相同 |
| **单轨道 A/B（原始引擎 vs 优化引擎）** | 28.1 s → **11.0 s，`-19/7560` 完全相同，2.5×** |

| `class_integral --validate` | C5 = 1/36 ✓ |

## 3. 顺带发现：引擎自检的目标一直是错的

`class_integral.py --validate` 的 `{4,2}` 条目拿 **单个置放** 的值
（−2/315）去比 **束值** 目标（−23/420）——**从写下那天起就在静默失败**，
而且它从来没进过 `run_all.sh gates`，所以没人看见。

用原始引擎复现同一失败，确认与本轮改动无关。独立算出束值验证引擎无误：

    {4,2} on the 6-cycle: 15 placements, 3 orbits
      size 6  [[0,1,2,3],[4,5]]  = -2/315
      size 6  [[0,1,2,4],[3,5]]  = -1/1260
      size 3  [[0,1,3,4],[2,5]]  = -1/252
      bundle = -23/420  MATCH

**修**：`CLASSES` 加 `BUNDLE` 标志，`--validate` 对束值类先枚举轨道再求和；
另补 `{2,2,2} = 32/105` 一条。纯类（C5、{6}）单置放即束值，这正是它们
一直"过"、把问题掩住的原因。

## 4. 还没做的杠杆，按预期收益排序

1. **证书过滤的满维性判定（预期 2–4×，直击剩下的 44%）**：先用 float64
   解一遍严格性 LP；若得到内点 x 且松弛 ≥ δ，把 x 有理化后**精确验证**
   全部约束——验证只是一次矩阵-向量乘，比精确单纯形便宜两个量级。
   验证通过即**严格证明**满维，无需精确 LP；失败才回退。
   不满维一侧同理用 Farkas 对偶证书。**这条是严格的，不是启发式。**
2. **扁平任务池（预期墙钟 1.2–1.5×）**：`run_k10` 每个轨道一个 barrier，
   项的成本差异大（0/1/2 个辅助维），尾部拖累使多数 worker 空转。
   改为 101×676 的单一任务池即可消除。
3. **Bareiss 整数保型单纯形（预期 1.5–2×）**：消掉内层 gcd。
4. **C/Rust 重写（预期 3–10×，风险高）**：只对非 LP 的那约 50% 有效，
   且要重做全部验证。**在 (1)(2) 之前不值得。**
5. **GPU**：递归不规则、哈希记忆化、精确判定——依然不适合。唯一可 GPU 化的
   是 (1) 里的 float 预解，但那部分本来就便宜。

## 5. 一项配套改动

`run_k10.py` 加了**增量检查点与续跑**（`ck_<class>.json`，逐轨道落盘）。
原来全部结果留在内存里直到最后一个轨道完成，被杀即全丢——这正是
"要不要用新引擎重启在跑的作业"难以决断的原因。现在重启不再是全损。

## 6. 二次剖析：瓶颈转移，以及为什么在这里收手

记忆化上线后重新剖析（4 个热项，1.54 s）：

| 部件 | 优化前 | 优化后 |
|---|---|---|
| 精确单纯形（满维性） | 44% | **19%**（77% 的调用被记忆化吃掉）|
| `facets()` 面枚举 | ~30% | **43%**（升为首位）|
| 记忆化键构造 `_fd_key` | — | 15% → **削掉**（见下）|

**键的构造一度成了新开销。** 第一版把每行归一到本原整数向量，多抓到几个
碰撞，却花掉 15% 的总时间。改为直接用已约分的 mpq 值做键——**命中率一模一样
（2951/3836，77%）**，端到端从 2.5× 升到 **2.61×**。

**重要修正**：我先前估"证书过滤的 LP 值 2–4×"是**在旧的成本结构下估的**。
记忆化已经把 LP 从 44% 压到 19%，同一条杠杆现在**最多只值约 1.2×**。
按 Amdahl，继续在 LP 上用力不划算；真正的下一个目标是 `facets()`（43%）。
**这是收手并提交运行的理由，不是偷懒。**

## 7. 部署（r141）

引擎 (`class_integral.py`、`exact_lp.py`、`facet_recursion.py`、`run_k10.py`)
分发至 220/230/231/238。

**播种式重启**：把原始引擎已算出的轨道写进检查点，但**故意留出每类前两个
轨道**让新引擎重算——这样重启不但省掉大部分重复工作，还顺带在真实生产轨道上
做一次新旧引擎对撞。

| 作业 | 主机 | 播种 | 重算做对撞 |
|---|---|---|---|
| `{4,4,2}` | 220，90 jobs | 22/101 | O0, O1 |
| `{6,2,2}` | 230，20 jobs | 10/46 | O0, O1 |

**又一次 pkill 自匹配**，换了个面目：模式 `"[q]220.sh"` 本身是加了括号的，
但我在**同一条命令行的别处**写了未加括号的字面串（`cat .../q220.sh`），
于是 pkill 匹配到自己的 ssh 命令行，会话被杀（exit 255）。
**纪律升级**：不只是模式要加括号，**命令行任何位置都不得出现该字面串**。

另外确认一遍：220 上有个队列脚本在守着，**必须先杀队列再杀 worker**，
否则队列会自动推进——与 231 那次同一条。
